# 测试 / 质量保障技术指南

> 适用项目：《时痕实验室：昨日的我》  
> 固定主责：成员 E（测试 / 质量保障）  
> 对应分支族：`test/*`  
> 本指南交付分支：`codex/test-technical-guide`（按要求基于 `main`）  
> 执行对象：日常测试仍针对最新 `develop`、相关 PR 分支或明确的发布候选提交

## 0. 使用方法与测试门禁

本指南与三份开发指南采用相同闭环：一次只处理一个测试模块，先理解技术原理，再让 AI 生成该模块的测试草案或清单，最后由测试人员在真实代码和目标电脑上执行、检查和验收。

### 0.1 每张测试任务的强制流程

1. 从第 5 节只选择一个 T 模块，并建立一张只属于“测试”板块的任务卡。
2. 阅读 README 对应规则、本指南第 1～4 节、目标模块和相关开发指南章节。
3. 明确被测提交哈希、环境、固定数据、允许修改路径、预期结果和停止条件。
4. AI 只能生成本模块的测试、测试数据或测试文档；不能修改生产代码或改写产品需求。
5. 成员 E 审查断言是否真正覆盖规则、边界和失败分支，删除只断言“非空/不抛异常”的伪测试。
6. 实际执行命令和手工步骤，保存原始结果摘要；不得把 AI 的推测写成“已通过”。
7. 失败时先最小化复现，再建立缺陷；不得直接进入业务目录修复。
8. 回归时引用缺陷 ID、修复提交和原失败用例，记录通过/失败/阻塞。

README 的冻结玩法与验收标准最高；已批准公共契约次之；然后是本指南和任务卡。若开发指南与 README 冲突，以 README 为准并阻止合并，等待项目经理修订指南。

## 2. 测试职责与修改边界

### 2.1 测试主责

- 建立测试计划、冒烟清单、固定数据、缺陷模板和发布报告；
- 审核每个 PR 的验收条件和开发者测试，不只接受口头说明；
- 维护跨模块、回归、兼容、性能、暗调/非颜色可读性和五关手工测试；
- 对结果给出“通过 / 有条件通过 / 不通过 / 阻塞”之一；
- 对缺陷进行阻塞/高/中/低分级并跟踪回归；
- 第 6 天完成功能冻结验收，第 7 天以后优先阻塞和高缺陷；
- 第 8 天提交可追溯的测试报告和演示证据。

开发者仍必须为自己的纯逻辑修改补单元测试：开发 1 负责路径/输入/碰撞，开发 2 负责时钟/记录/寿命/快照，开发 3 负责机关/schema/存档。测试主责不替代这些责任。

### 2.2 允许路径

测试任务卡可列出：

```text
src/test/java/org/example/timeloop/**
src/test/resources/**
docs/testing/**
```

如果需添加测试依赖或插件，只能提出变更需求，由项目经理批准一张独立工程任务。测试人员默认禁止修改：

```text
pom.xml
src/main/java/**
src/main/resources/levels/**
src/main/resources/css/**
src/main/resources/images/**
src/main/resources/audio/**
```

复现缺陷时可以在测试目录建立失败用例；不能为了变绿而放宽 README 规则、删除断言或直接改生产代码。

### 2.3 测试数据与契约

- 时间、持续和容差以整数 tick 表达；显示秒数不是断言依据。
- ID 必须稳定，测试不依赖对象地址、集合偶然顺序或本地化文字。
- 测试使用人工时钟/固定帧间隔序列，禁止 `Thread.sleep` 等待游戏逻辑。
- 随机数据若确有必要必须固定种子并打印种子；MVP 核心规则本身不应随机。
- 位置比较使用团队冻结的世界坐标容差；建议灰盒初值为 `1e-6 × tileSize`，最终由开发 1 和测试共同确认。节点 ID、tick、轮次、状态和事件顺序必须精确相等。
- UI/视觉的像素误差不能反向成为碰撞或共振容差。
- 每个固定数据文件要写 `schemaVersion` 或明确版本，并随契约变更同步评审。

## 3. 测试技术原理

### 3.1 测试金字塔与证据链

优先级从下到上：

```text
大量纯逻辑单元测试
  -> 少量模块契约测试
  -> 关键跨模块固定场景
  -> 五关端到端手工/集成
  -> 目标电脑演示与长时运行
```

JavaFX Node/Canvas 不应成为每个测试的前置条件。固定步长、路径、记录、寿命、机关和存档先用纯 Java 测试；Canvas 只读性、页面焦点、缩放、声音和视觉可读性再做集成/手工检查。8 天版本不为 UI 自动化额外引入重量级框架，除非项目经理批准且不影响主线。

一条发布结论的证据链是：README 规则 → 用例 ID → 固定输入/步骤 → 实际结果 → 被测提交 → 缺陷/回归记录。

### 3.2 测试命名与结构

- 测试类按被测行为命名，例如“共享时钟”“方向优先级”“共振状态机”；不按开发者姓名命名。
- 测试方法采用 `given_when_then` 或等价中文可读结构，名称必须说明条件与结果。
- 一个测试只验证一个核心原因；可有多个相关断言，但失败时必须看出是哪条规则破坏。
- Arrange 使用最小路径/记录/机关；Act 通常推进明确 tick；Assert 检查状态、事件和清理。
- 参数化测试适合出口优先级、阶段转移、寿命表、autoDock 和射线边界；不得用一条巨大循环掩盖具体失败样例。
- 对每个已修缺陷保留一个最小回归用例，不能修完后删除。

### 3.3 固定步长、阶段和路径测试原理

同一输入脚本分别喂入模拟 30/60/120 FPS 的渲染时间序列，比较的是逐 tick 规范状态，不是最终截图。

必须验证：

- `TUTORIAL/READY/PAUSED` 不推进、不记录；`PLAYING` 从 tick 0 开始；
- 逻辑帧索引严格为 `0..durationTicks-1`，没有重复/跳跃；
- 严重掉帧时允许视觉时间变慢，不允许直接跳逻辑 tick；
- 松开方向键后速度仍为 `baseSpeed`；
- 锁定区约 `0.15 × tileSize`，跨节点检测不依赖浮点恰等；
- 出口优先级严格为“有效队列 → 直行 → 唯一侧路 → defaultExit → 死路返回”；
- 内部墙、边界墙和关闭门均不可穿；门在前一决策点被排除，不能成为等待点；
- 无完整网格时逻辑仍相同，视觉开关不能改变路径与碰撞。

### 3.4 输入、autoDock、相位和射线测试原理

输入测试必须区分“新按下边沿”和“持续按住”。autoDock 使用如下矩阵：

| 前置 | 输入/事件 | 预期 |
| --- | --- | --- |
| CRUISING，按住 W | 进入 autoDock | 进入 DOCKED，速度 0，清空队列，机关激活 |
| 刚进入，W 仍按住 | 推进多个 tick | 不离开，不重复激活 |
| DOCKED | 新按非法方向 | 保持 DOCKED，给出无效反馈 |
| DOCKED | 新按合法方向 | 同 tick 释放占用并以 baseSpeed 离开 |
| 残影记录含停驻段 | 共享 tick 推进 | 在相同 tick 进入、静止、离开，不读键盘 |
| 残影被淘汰/整局重开 | 清理 | 占用释放，无旧状态 |

相位/射线矩阵：

| 维度 | 必测边界 |
| --- | --- |
| Space | 新边沿触发；按住不重复；恢复中无效；恢复结束后可再触发 |
| 时长 | PHASED 恰好 30 tick；RECOVERING 恰好 45 tick；暂停不消耗 |
| 运动 | 相位前后位置连续、当前速度不变、方向队列保留 |
| 碰撞 | 只忽略激活射线；墙、关闭门、autoDock、终端和共振仍有效 |
| 命中 | 非 PHASED 变为 0.50× 持续 120 tick；同周期一次；不叠加/刷新 |
| 失败/记录 | 命中不死亡、不 FAILED、不中断定长录制 |
| 残影 | 只回放相位/时滞结果，不重新判定射线 |
| 关卡 2 | 相位后可按时到达；命中通常超过本轮；正式解最多两次 Space；成功率门禁 |
| 关卡 5 | 相位避开时超过共振窗口；接受时滞后进入窗口 |

### 3.5 记录、边界、寿命与快照测试原理

记录不只验证长度，还验证每个索引的 tick、DOCKED 静止段、离开后的继续运动、相位/时滞状态和事件排序。

边界矩阵：

| 情况 | 缓冲 | 新残影 | 状态清理 |
| --- | --- | --- | --- |
| 非最终轮自然到时 | 恰好 D 帧并封装 | 是 | 恢复轮内，保留会话 |
| 提前通关 | 不完整即丢弃 | 否 | 进入 RESULT |
| 最终轮自然到时未通关 | 不生成无用记录 | 否 | 进入 FAILED |
| 暂停 | 保持不变 | 否 | 所有逻辑冻结 |
| 从第一轮重开 | 丢弃 | 否 | 清会话、回第 1 轮 READY、存档保留 |
| 退出关卡 | 丢弃 | 否 | 清会话、返回页面 |
| 射线命中 | 继续记录 | 否（直到自然到时） | 不 FAILED |

寿命公式必须按 README 原样用固定表验证：

```text
age = r - s
active = 1 <= age <= L
remainingRounds = L - age + 1
lifeProgress = clamp(((age - 1) * D + roundTick) / (L * D), 0, 1)
bodyAlpha = 0.82 - 0.32 * lifeProgress
```

至少覆盖 L=1/2、tick 0、D-1、轮次边界、第 3 轮 E1+E2、第 4 轮 E2+E3。E1 在第三/五关第 3 轮是最后有效轮，轮末先于 E2 淘汰并释放占用。

完整重开逐项断言玩家、方向队列、相位/恢复、残影、录制、轮次、机关、共振、射线、提示和计时；不能只断言“回到了 READY”。

### 3.6 共振与关卡时间表测试原理

共振使用固定区域和 actor aura 的逻辑相交，测试不使用轨迹像素宽度。

| 场景 | 预期 |
| --- | --- |
| 当前玩家进入 | 仅预览，不改变 DORMANT/ARMED/LATCHED |
| 一个残影进入 | DORMANT → ARMED，窗口 30～45 tick |
| 同来源再次进入 | 不能锁存、不能刷新窗口 |
| 不同来源在窗口内进入 | ARMED → LATCHED |
| 不同来源在窗口外进入 | 已超时回 DORMANT，不锁存 |
| 同 tick 两残影进入 | 先批量按 sourceRound 稳定排序，结果确定 |
| LATCHED 后 actor 离开 | 保持到本轮结束 |
| 下一轮开始 | 恢复 DORMANT |
| 只有共振 | 出口仍关闭 |
| 共振 + 单中继 | 出口仍关闭 |
| 共振 + 双中继 + 当前玩家核心 | 出口条件满足 |

第四/五关还要验证每条准备记录包含“共振区 + 对应中继”两个锚点。第五关固定到达刻必须同时满足“避开时超窗、接受同一时滞后入窗”，并排除共振前 autoDock、撞墙等待或普通绕路替代。

### 3.7 五关、页面与存档测试原理

- 关卡清单、选关 UI、资源和存档中可进入的关卡必须恰好是 README 五关。
- 从 MENU → LEVEL_SELECT → TUTORIAL → READY → PLAYING → RESULT/FAILED 的合法转移逐项验证；非法转移有明确处理。
- HUD 常驻区只有一个共享秒级读秒；轮数、sourceRound 和 remainingRounds 不是第二套秒表。
- 射线命中不能进入失败页；只有 `maxRounds` 最后一轮到时未通关才 FAILED。
- 暂停、教程跳过/重播、整局重开和返回选关不得残留 listener、输入或会话状态。
- 存档只含设置、通关和教程查看状态；在临时目录测试正常 round-trip、空文件、截断 JSON、缺字段、未知字段、不可写路径和旧版本。
- 原子写入失败时旧文件仍可读；损坏时安全回退而不是阻止启动。

### 3.8 视觉、可访问性、性能与兼容测试原理

视觉不是只看“好不好看”，而是验证规则能否被读懂：

- 不显示全屏网格时，五名成员都能在 3 分钟理解节点/排队方向，至少四人认为操作可预测；
- 五人共 25 次第二关测试，理解后无时滞通过率至少 80%；
- 当前玩家、E1、E2 用编号、实/虚线、alpha、外环和错位区分，不能只靠颜色；
- DORMANT、ARMED、LATCHED、超时用分段形状、线路、波纹和声音区分；
- 第二/五关射线外观、图标、预警、音效和命中反馈相同；
- 缩放/分辨率变化下 HUD 不遮挡、Canvas 不裁切、逻辑坐标不变；
- 关闭声音时仍能靠视觉理解，音频设备不可用不阻塞游戏；
- 10 分钟连续试玩与多次场景切换后，无旧轨迹、旧粒子、旧 listener 或持续增长的对象/内存趋势；
- 性能下降时不能通过跳逻辑 tick、少录帧或降低碰撞频率掩盖。

性能结论必须注明目标电脑、分辨率、缩放、JDK 和场景；不要只写“很流畅”。

### 3.9 缺陷严重级别与发布判断

| 级别 | 定义 | 示例 | 处理 |
| --- | --- | --- | --- |
| 阻塞 | 无法构建/启动/继续主流程或数据破坏 | Maven 不可构建、关卡必卡死、存档使程序无法启动 | 阻止合并/发布，立即处理 |
| 高 | 核心规则错误、主解失效、确定性破坏 | 回放漂移、可主动停车、第二轮共振、射线死亡 | 阻止候选版，优先修复 |
| 中 | 有绕过方式但明显影响体验/理解 | 某提示错误、非主路径 UI 异常 | 第 7 天后谨慎评估 |
| 低 | 不影响规则和演示的轻微表现问题 | 小范围对齐、低频装饰瑕疵 | 不阻塞，不挤占回归 |

“有条件通过”必须写清条件、风险所有者和截止时间；不能作为隐含的“先合并再说”。环境未具备、接口未交付或数据缺失时使用“阻塞”，不要把未运行写成“失败”。

## 5. 单模块测试实施卡

### 5.1 T0：环境与测试基线

**目标**：建立能区分“环境阻塞、测试失败、尚未实现”的测试入口和记录格式。

**技术原理**：可重复测试依赖统一工具链、固定时钟、稳定数据和提交身份；IDE 里偶然绿灯不是团队基线。

**步骤**：记录环境 → 提交 JUnit 5/POM 差距单 → 确认 Maven 方式 → 核对 CLI/IDE 测试发现数 → 建固定数据约定 → 冒烟清单 → 缺陷模板 → 首份基线报告。

**边界**：`mvn` 不存在、Wrapper 空、JUnit 3/5 混用、零测试仍返回成功、只在一台电脑可运行。

**自动产出**：最小真实断言的 Jupiter 冒烟用例（迁移任务批准后）；测试报告路径与数量核对。

**手工验收**：新克隆按文档可运行构建/测试/窗口；关闭窗口进程正常退出。

**完成定义**：没有修改业务代码；所有“通过”都有关联命令和提交；环境问题未伪装成产品缺陷。

### 5.2 T1：核心灰盒门禁

**目标**：在批量关卡和双残影前验证恒速巡行、路径、输入、碰撞和相位可预测。

**步骤**：人工时钟多帧率 → 路径优先级参数化 → 10/1000 次节点越过 → 墙/门/死路 → 单槽队列 → E 缓冲 → 相位 30/45 tick → 射线灰盒 → 隐藏网格试玩。

**边界**：浮点越点、持续按键、失焦、暂停恢复、关闭门前无出口、相位期间墙重叠。

**自动产出**：核心矩阵与首个分歧 tick 报告。

**手工产出**：五人理解记录、25 次无时滞通过记录和操作误解清单。

**完成定义**：README 原型门禁全部有证据；失败时停止正式关卡/多残影，而不是放宽规则。

### 5.3 T2：单残影、前两关和重开

**目标**：证明完整固定时间线及 autoDock/相位/时滞结果可确定回放。

**步骤**：D 帧记录 → DOCKED 静止/离开 → 单残影逐 tick 对照 → 普通轮事务 → RESULT/FAILED/重开/退出矩阵 → 第一关因果链 → 第二关相位与命中对照。

**边界**：D-1/D、末 tick 交互、射线命中后记录、最终轮、暂停重开、残影误操作终端。

**自动产出**：定长/丢弃、事件顺序、单残影、清理回归测试。

**手工验收**：第一关当前/过去协作；第二关正确相位和故意命中的两种完整结果。

**完成定义**：单残影门禁独立通过，才允许 T3；没有射线死亡或提前结束本轮。

### 5.4 T3：双残影、寿命、共振与必要时滞

**目标**：验证第三至五关的时间机制不能退化为普通队友/按钮。

**步骤**：寿命公式边界 → E1+E2/E2+E3 → 淘汰释放 → 第三关补救 → 共振状态表 → 双中继/核心 → 第四关宽容时序 → 第五关避开/接受固定到达刻 → E1 消散压力。

**边界**：同来源、同 tick、窗口刚好边界、第二轮玩家预览、锁存后离开、轮末复位、E1 淘汰仍占中继。

**自动产出**：公式参数化、共振状态机、到达刻数据和因果链测试。

**手工验收**：未参与设计者能解释哪条早/晚、缺哪个中继以及 E1 消失后的后果。

**完成定义**：删除 sourceRound、改常驻角色或改按钮会让测试失败；共振本身永远不能直接开出口。

### 5.5 T4：页面、存档与恰好五关集成

**目标**：验证完整用户流程、数据恢复和关卡清单一致。

**步骤**：合法状态流 → 菜单/选关 → 教程/READY → 五关通关 → FAILED/重开 → 返回菜单再进关 → 存档临时目录矩阵 → 关卡/资源/存档 ID 一致性。

**边界**：快速重复命令、损坏存档、目录不可写、教程跳过/重播、完成第五关、重开后 listener/输入残留。

**自动产出**：状态命令、schema、存档回退、恰好五关检查。

**手工验收**：从全新进度到完成五关再重启，页面、解锁和设置一致。

**完成定义**：不存在第六关、成绩/收集数据或射线失败页；会话状态不会写入存档。

### 5.6 T5：可读性、兼容、性能与资源清理

**目标**：确保答辩目标机上机制可读、运行稳定且不依赖颜色/声音单一通道。

**步骤**：多缩放/分辨率 → 暗调对比 → 关闭颜色提示对照 → 静音/无音频 → 轨迹重叠 → 10 分钟长时 → 反复五关/重开/菜单 → 对象/内存趋势 → 资源许可证。

**边界**：E1 alpha 最低、两个轨迹完全重合、粒子大量触发、音频缺失、窗口失焦/恢复、存档目录权限。

**自动产出**：轨迹降采样稳定、渲染快照只读、粒子/缓存上限等可纯逻辑验证项。

**手工产出**：截图/录屏编号、环境数据、观察者结果和性能趋势；不把截图像素当玩法判定。

**完成定义**：关键状态至少有两种表达方式；长时运行无高优先级泄漏/卡顿；性能优化不破坏 tick。

### 5.7 T6：回归、发布验收和测试报告

**目标**：对唯一候选提交给出可追溯的发布结论。

**步骤**：冻结提交 → `mvn test`/package → 启动冒烟 → 阻塞/高缺陷回归 → 五关全通 → 兼容/性能抽测 → 存档升级/损坏 → 演示路线录制 → 汇总未解决风险 → 签字。

**边界**：测试期间候选提交变化、只回归修复点不看相邻规则、缺陷无修复哈希、报告引用旧结果。

**产出**：测试摘要、环境、用例结果、缺陷统计、未解决风险、五关记录、性能观察、最终“通过/不通过”。

**完成定义**：被测哈希固定；阻塞/高为 0；19 条 README 验收标准逐项有证据或明确不通过。
