## 0. 如何使用本指南

本指南不是“让 AI 一次生成整个引擎”的需求书，而是开发 1 每次领取一张单模块任务卡时的操作手册。README 中的产品范围和规则优先级最高；本指南只解释如何在开发 1 的边界内实现和验收。

### 0.1 每张任务卡的强制顺序

1. 只选择本指南第 5 节中的一个模块；若目标同时命中两个模块，项目经理必须继续拆卡。
2. 阅读 README 中该模块对应的规则、本指南第 1～4 节、第 5 节对应模块和第 6 节验收方法。
3. 在任务卡中写明允许修改的精确路径、禁止路径、已确认接口和可观察验收条件。
4. 让 AI 只为这张任务卡生成代码或测试，不得顺手创建未来类、重构其他板块或修改公共契约。
5. 开发者逐文件审查差异，能解释更新顺序、状态变化、边界条件和错误处理。
6. 执行自动化测试和手工验证，记录命令、结果、环境与未解决风险。

### 1.4 JavaFX 线程边界

- `AnimationTimer.handle`、输入事件、场景切换和 `Canvas` 绘制发生在 JavaFX Application Thread。
- 8 天版本不引入额外游戏逻辑线程；固定步长更新与绘制可在 JavaFX 线程顺序执行，以减少竞态。
- `core` 中的时钟、路径、碰撞、输入状态和状态机不得依赖 `Scene`、`Node`、`Canvas`、`KeyEvent` 等 JavaFX 类型，使其可在 JUnit 中直接构造。
- JavaFX 事件只在边界层转成不可变的逻辑输入；逻辑层不保存 `KeyEvent`。
- 若未来需要后台资源读取，后台线程只产出不可变数据，切换场景仍回到 JavaFX 线程；这不是当前开发 1 可自行扩展的任务。

### 2.4 每逻辑刻的数据顺序

项目经理应冻结唯一顺序。推荐的最小顺序是：

```text
采集本 tick 输入边沿
  -> 读取不可变 TickContext 与关卡几何
  -> 更新当前玩家方向队列/相位状态
  -> 沿路径推进并在节点提交转向
  -> 解析墙、门、autoDock、终端与射线候选
  -> 统一发布本 tick 事件
  -> 开发 2 在 tick 末记录规范玩家状态
  -> 生成只读 RenderSnapshot
  -> Canvas 绘制（可插值，不能回写逻辑）
```

同一 tick 多事件的排序必须稳定，建议按事件类别再按稳定实体 ID 排序；不得依赖 `HashMap` 迭代顺序。

## 3. 核心技术原理

### 3.1 固定步长而非固定帧率

目标逻辑频率是 60 Hz，`step = 1/60 s`。`AnimationTimer` 提供的时间只累积到 accumulator；只要 accumulator 足够就执行一个完整逻辑刻。渲染次数可以变化，但记录不能跳 tick 或重复 tick。

实现约束：

- 首帧只记录时间基准，不补算从 0 到当前系统时间的逻辑；
- 单帧时间差设置上限，避免窗口拖动后出现巨量补帧；
- 每帧补算次数设置有限上限；达到上限时让游戏视觉时间暂时变慢，不允许把 `roundTick` 直接跳到未来；
- `READY`、`TUTORIAL`、`PAUSED` 清理或冻结 accumulator 的策略必须统一，恢复后不得补算暂停时长；
- 渲染插值只影响画面，不改变记录位置、碰撞位置或 tick。

### 3.2 正交路径图与确定性巡行

正式画面不显示完整网格，但逻辑仍使用对齐网格的路径中心线。玩家位于一条有方向的路径段上；每个节点保存合法出口、可选 `defaultExit` 和稳定 ID。

节点决策优先级固定为：

```text
有效排队方向 -> 继续直行 -> 唯一合法侧路 -> defaultExit -> 死路原路返回
```

- 玩家主动排队只接受直行或 90° 转向；普通路口不能主动 180° 掉头。
- 在距节点中心约 `0.15 × tileSize` 时锁定本次选择；到中心点才提交转向并吸附到中心线。
- 一次推进若跨过节点，必须按“旧位置到新位置的有向距离”检测越过并消耗剩余距离，不能依赖浮点位置恰好等于节点坐标。
- 关闭门要在前一个决策节点从可行出口中移除；角色不能先撞到门再静止等待。
- 无合法前路的真正死路自动掉头；内部墙和边界墙不能被穿过。

### 3.3 输入是边沿与意图，不是速度开关

- `W/A/S/D` 与方向键产生方向意图；松键不把速度设为 0。
- 单槽队列只保留最新的尚未提交方向。
- `Space`、`E` 和从 autoDock 离开的方向都使用“本 tick 新按下”边沿；按住不能重复触发。
- 逻辑层同时接收 `pressedThisTick` 和 `heldKeys`，以区分新按下与持续按住。
- `E` 交互意图可保存 6～10 tick；在宽容半径内命中一次后立即消费，过期后清除。

### 3.4 autoDock 的防误离开语义

玩家进入 `autoDock=true` 的机关时：

1. 吸附到定义的停驻点并进入 `DOCKED`；
2. 速度变为 0，清空方向队列；
3. 保存进入瞬间正在按住的方向键集合；
4. 之后只有一个新发生且在出口中合法的方向 key-down 才能离开；
5. 离开同 tick 释放占用并立刻恢复 `baseSpeed`。

持续按住进入前的方向键不能离开。残影不重新运行这套输入逻辑；开发 2 按录制帧和事件复现停驻与离开。

### 3.5 相位下潜与射线

相位状态只影响“当前玩家是否会被激活射线结算”，不影响路线和墙门碰撞。冻结参数为 `phaseDurationTicks=30`、`phaseRecoveryTicks=45`，除非进入关卡前由已批准配置覆盖。

```text
AVAILABLE --Space 新边沿--> PHASED(30 tick)
PHASED --到期--> RECOVERING(45 tick)
RECOVERING --到期--> AVAILABLE
```

- `PHASED` 中继续以进入前的当前速度运动，方向仍可排队。
- 不允许穿墙、穿关闭门、取消已有时滞或改变 `baseSpeed`。
- 非 `PHASED` 的几何命中只提交命中候选；开发 3 的射线状态负责同一激活周期最多结算一次。
- 项目没有生命、伤害和射线即时失败。
- 残影只显示已记录的相位/减速结果，不能再次参与射线碰撞。

### 3.6 Canvas 渲染是只读投影

图层顺序严格遵循 README：背景；地面/墙/局部节点；残影轨迹；机关；角色/残影；特效；HUD。开发 1 不绘制全屏格线。

- 世界坐标与屏幕坐标由摄像机转换；碰撞永远使用世界坐标。
- 每次设置 `globalAlpha`、虚线或变换前保存绘图状态，用后恢复，避免污染后续图层。
- 轨迹每 3～6 tick 降采样一次并缓存；不能每帧扫描每条时间线的所有原始帧。
- 新/旧残影除颜色外还要用实线/虚线、编号、透明度和 2～4 px 平行错位区分。
- 生命周期 alpha 由开发 2 的 `lifeProgress` 派生，渲染只应用，不能自行计时。
- 消散只使用 20～40 个可复用小菱形/光点；粒子耗尽后必须归还池或解除引用。

## 5. 单模块实施卡

每个模块都必须单独开任务。下面的“接口候选”只有在项目经理记录批准后才能作为编码依据。

### 5.1 C0：工程与 Canvas 门禁

**目标**：证明开发 1 可以在目标包中提供纯逻辑核心和 Canvas 边界，而不接管场景管理。

**技术原理**：启动/场景属于 `app`，游戏规则属于纯 Java，绘制适配属于 `render`。最小窗口不是完整架构。

**实现顺序**：核对 JDK/Maven方式 → 确认目标包 → 项目经理建立最小入口 → 开发 1 接入空 Canvas/无状态渲染器 → 启动与退出验证。

**边界情况**：JavaFX 依赖无法解析、错误主类、窗口关闭后进程残留、测试误需 JavaFX Toolkit。

**自动验证**：纯逻辑测试不初始化 JavaFX；Maven 构建与测试命令退出码为 0。

**手工验收**：窗口只出现一个；缩放下 Canvas 尺寸正确；关闭后无残留进程。

**完成定义**：现状差距有决策记录；没有业务类批量占位；路径变更均在任务卡范围内。

### 5.2 C1：固定步长接入

**目标**：渲染帧率波动时，每个逻辑刻仍恰好执行一次，并与开发 2 的共享 tick 契约对齐。

**依赖**：已批准的 `TickContext`/游戏阶段读取接口；开发 1 不维护第二个权威 `roundTick`。

**实现顺序**：定义纳秒到秒转换 → 首帧初始化 → 累加帧间隔 → 有界补算 → 每 tick 调用更新端口 → 只读渲染插值 → 阶段切换清理 accumulator。

**边界情况**：第一帧巨差值、窗口拖动、暂停恢复、READY 到 PLAYING、一次帧跨越轮次边界、严重掉帧。

**自动测试**：用人工时间源输入 30/60/120 FPS 序列；相同逻辑秒数产生相同 tick 数；暂停间隔不补算；补算上限不跳 tick。

**手工验收**：限制不同渲染帧率录制同路线，开发 2 的回放检查得到相同位置与交互 tick。

**完成定义**：无独立游戏秒表；无按帧移动；记录层从未看到重复或跳跃 tick。

### 5.3 C2：恒速巡行、路径节点与碰撞

**目标**：玩家松键仍以 `baseSpeed` 沿中心线运动，能稳定转向、绕过关闭门并在死路返回。

**依赖**：开发 3 提供不可变 `LevelGeometry`；单位、节点 ID、墙/门阻挡语义已冻结。

**实现顺序**：建立有向路径段 → 将玩家吸附到段中心线 → 用距离推进 → 进入锁定区选择出口 → 越过检测并吸附节点 → 消耗剩余距离 → 处理多节点极端情况 → 加入墙/门查询。

**边界情况**：浮点误差越过节点、高帧间隔跨两节点、无 `defaultExit` 的多侧路、门在接近中关闭、零长度段、地图非法孤点。

**自动测试**：优先级表逐项覆盖；连续 10 次和 1000 次转向无漂移；松键速度不变；普通路口主动掉头被拒绝；墙和关闭门不可穿；死路自动返回；非法图明确失败而非静止。

**手工验收**：隐藏完整网格后，五名成员均能在 3 分钟理解标记；25 次试玩无时滞通过率至少 80%，无人靠顶墙等待。

**完成定义**：所有决定由路径图和稳定规则产生，不依赖画面像素或散列迭代顺序。

### 5.4 C3：方向输入、E 缓冲与 autoDock

**目标**：输入可预测；进入驻留机关不会被旧按键误带出，离开时可被准确记录。

**依赖**：开发 3 的 autoDock 区域/合法出口和事件含义；开发 2 的帧/事件记录字段。

**实现顺序**：JavaFX 键转逻辑键 → 维护 held/pressed/released → 单槽方向队列 → E 缓冲 → 进入区域边沿 → DOCKED + 清队列 + 旧键快照 → 新合法方向边沿离开 → 发布稳定事件。

**边界情况**：WASD 与方向键映射同一意图、同 tick 进入又按键、按住键进入、无合法出口、两个 autoDock 重叠、暂停时键状态、失焦导致 release 丢失。

**自动测试**：新输入替换旧队列；无效方向反馈后丢弃；E 在 6～10 tick 窗口命中一次；持续旧键不离开；释放再按或另一新合法方向才离开；离开恢复固定速度并释放占用。

**手工验收**：第一关完整复现“进入—停到若干 tick—新按键离开”，回放离开 tick 与原记录一致。

**完成定义**：普通廊道无停车输入，autoDock 是唯一主动等待点；没有轮次提前结束键。

### 5.5 C4：相位状态与统一射线碰撞

**目标**：一次 `Space` 触发低操作量相位，正确忽略射线但不改变其他碰撞和运动。

**依赖**：射线的 `OFF/WARNING/ACTIVE`、周期和结算属于开发 3；时滞后的记录属于开发 2。

**实现顺序**：Space 边沿 → 三态计数器 → 每 tick 先更新状态 → 继续正常移动/转向 → 始终检查墙门 → 激活射线几何相交 → PHASED 时忽略结算，否则发候选 → 表现读取状态。

**边界情况**：按住 Space、恢复最后一 tick、进入 PHASED 前已减速、同周期多帧相交、相位跨轮次、暂停、残影进入射线。

**自动测试**：PHASED 恰好 30 tick，恢复恰好 45 tick；按住只触发一次；位置连续且队列保留；墙门仍阻挡；残影不进入结算；普通命中不触发 `FAILED`。

**手工验收**：第二关一次相位可覆盖相邻双束门且成功余量满足关卡规格；第五关同一射线外观与碰撞逻辑未分叉。

**完成定义**：没有跳跃高度、护盾、生命值、冲刺或第二套闪避动作。

### 5.6 C5：Canvas、轨迹与状态表现

**目标**：用开发 2/3 的只读数据清晰呈现内部墙、当前玩家、两代残影、射线、共振和因果链。

**依赖**：开发 3 状态稿和开发 2 `RenderSnapshot`；开发 1 不推导机关玩法状态。

**实现顺序**：坐标转换 → 固定图层 → 几何墙/地面 → 轨迹降采样缓存 → 机关 → actor → 状态效果 → HUD 插槽 → 缓存失效/场景清理。

**边界情况**：两轨迹完全重合、alpha 状态泄漏、缩放模糊、路径越过墙被错误绘制、长时间粒子泄漏、关卡切换仍持有旧快照。

**自动测试**：降采样结果稳定；缓存键随时间线版本更新；渲染输入不可变；粒子池上限与回收可断言；绘制不改变玩法坐标。

**手工验收**：不靠颜色也能区分当前/E1/E2；老残影最低 alpha 仍可读；DORMANT/ARMED/LATCHED/超时可区分；暗调下 HUD 和唯一读秒清晰。

**完成定义**：不显示全屏格线、不创建第二数字计时器、不用特效补救逻辑错误，稳定运行无持续内存增长。

### 5.7 C6：性能、清理与发布修复

**目标**：在功能冻结后只消除核心阻塞和高优先级问题，保证答辩机器稳定。

**检查顺序**：固定步长积压 → 节点越过/漂移 → 输入边沿 → Canvas 缓存 → 粒子/场景引用 → 五关长时回归。

**性能预算**：以目标电脑实测为准；不得通过跳过逻辑 tick、降低碰撞频率或少录帧来换 FPS。先缓存静态层和轨迹，再减少低优先级粒子。

**自动验证**：长序列路径测试、不同帧间隔重放、缓存更新、场景清理和对象数上限。

**手工验收**：从主菜单连续进入五关、重开、返回并再进入；无旧轨迹、旧输入、旧粒子或卡死。

**完成定义**：第 7 天以后没有无关重构；修复有最小复现、回归测试和风险说明。

## 6. 验收、排错与交付

### 6.1 开发者必须补的测试

- 固定步长与人工时间源；
- 路径出口优先级、节点越过、中心吸附、关闭门和死路；
- 输入单槽队列、按键边沿、E 缓冲和 autoDock 防误离开；
- 相位 30/45 tick、墙门碰撞仍生效、射线候选去重边界；
- 轨迹降采样和缓存的纯函数逻辑。

测试主责负责跨模块矩阵、五关回归、性能/兼容性和最终结论。开发 1 不能把本板块单测全部转交测试人员。

### 6.4 人工代码审查清单

- 差异是否只属于一张任务卡和允许路径；

### 6.5 板块完成定义

开发 1 在第 8 天完成，必须同时满足：

1. 固定步长在不同渲染帧率下不跳逻辑 tick；
2. 玩家在普通廊道恒速、不靠墙或门等待，10 次连续转向稳定；
3. autoDock 清旧队列、新按键离开和 E 缓冲行为可测试、可回放；
4. 相位只忽略射线，不改变路线、速度、墙门碰撞或已有时滞；
5. 五关的几何、两代残影、轨迹、射线和共振反馈清晰且不反写玩法；
6. 性能优化没有牺牲记录完整性或确定性；
7. 开发者能现场解释路径优先级、固定步长、输入边沿和渲染只读边界；
8. 自动化与手工证据已由测试主责复核，没有阻塞或高优先级缺陷。
