## 3. 已完成的交付与不能倒退的契约

### 3.1 C0 的固定步长防御（历史经验，仍然有效）

`FixedStepClock` 是纯 Java 的 60 Hz 时钟。以下行为已有测试和注释，后续不要删除：

- 只有 `PLAYING` 可推进逻辑刻；冻结阶段更新时间基准，不补算暂停时长；
- 首帧仅建立时间基准；负或零时间差不制造负 accumulator；
- 单帧差值和补算次数都有上限；达到补算上限时清理剩余债务，宁可视觉时间变慢，也不能在恢复帧率后快进偿债；
- `interpolationAlpha()` 始终位于 `[0, 1)`。

这套防御不能替代 `RoundClock` 的权威 `roundTick`，更不能在玩家控制器中再建一只时钟。

### 3.2 C1：已冻结的 tick 调度与玩家状态契约

| 契约 | 当前事实 | 接手限制 |
| --- | --- | --- |
| `core.GamePhase` | 共 10 个阶段；只有 `PLAYING.advancesLogic()` 为 `true` | 不新增或重命名阶段，除非项目经理裁决 |
| `core.TickStepResult` | `NO_ADVANCE` / `ADVANCED` / `ROUND_END`；只有 `ADVANCED.shouldContinueFrame()` 为 `true` | 不在 `core` 或 `replay` 再造第二套结果枚举 |
| `core.TickUpdatePort` | 签名固定为 `TickStepResult stepOnce()` | 不改成 `void`，不让调用方猜测轮次边界 |
| `core.FixedStepLoop` | 复用 `FixedStepClock`；遇到 `NO_ADVANCE` 或 `ROUND_END` 会停止当前渲染帧的剩余补算 | 不维护第二只游戏时钟，不把额度带到下一帧 |
| `core.OrderedTickUpdatePort<C,E>` | 读上下文 → 消费输入 → 更新世界 → 发布/排序事件 → 记录 tick 末状态 → 生成快照 → 推进共享时钟 | `E` 与 Comparator 必须由外部注入；`core` 不能 import `replay` |
| `core.PlayerKinematics` | tick 末不可变规范状态；世界坐标为碰撞体中心；含方向、移动/相位/动画和交互结果 | C3 只产出它，不修改其公共字段而绕开记录契约 |

`Direction` 的值名为 `UP / RIGHT / DOWN / LEFT`。所有方向逻辑使用显式 `switch`，禁止 `ordinal()` 和依赖声明顺序。

**C2 PR**：[#28](https://github.com/time-trace-lab-team/time-trace-lab/pull/28)，`codex/dev1-c2 -> develop`，交接时仍为开放状态。C3 常规开发必须等它合入 `develop` 后再从最新 `develop` 建分支；如确需叠加开发，须由项目经理明确批准基于该 PR 的堆叠分支。

**实现位置**：

```text

src/main/java/org/example/timeloop/entity/**
src/test/java/org/example/timeloop/core/path/**
src/test/java/org/example/timeloop/entity/**
```

**完成行为与原理**：

- `OrthogonalPathGraph`、`PathNode`、`PathExit`、`PathPoint` 是不可变的纯 Java 路径模型；构造期拒绝零长度段、非正交连接、重复出口方向和缺失节点引用。
- `PatrolConfig.c2Greybox()` 冻结 `tileSize=48.0`、`baseSpeed=2.0` 世界单位/tick、`turnLockDistance=7.2`、`epsilon=0.000048`。`PatrolController` 由调用方传入共享 tick，不读取系统时间。
- 玩家松键仍按固定预算沿中心线移动。单槽队列保存最新未提交方向；进入锁定区时只选择一次，到节点中心才提交转向并吸附横向坐标。
- 节点出口严格按“有效队列 → 直行 → 唯一合法侧路 → 可通行 `defaultExit` → 真死路原路返回”决定。关闭出口由 `ExitPassability` 在决策节点排除。
- 单 tick 可跨一个或多个节点；每到中心都先提交方向，再继续消费剩余距离。最大到达次数由最短路径段给出上界，避免静默循环。
- 多条侧路同时可走、直行不可走、又没有可用 `defaultExit` 时抛出带节点上下文的异常，而不是把普通路口偷偷变成 180° 掉头。

**测试覆盖**：直线 60 tick 前进 120 单位、四向坐标、五级出口优先级、无效/反向队列、锁定后输入保留、中心转向、关闭出口、真死路、跨多节点预算、10/1000 次转向无漂移、非法图和逐 tick 确定性复现。

## 5. C3 的目标和固定数据流

C3 是“方向输入、E 缓冲与 autoDock”，目标是让输入可预测：进入驻留机关时旧按键不会误带角色离开；新合法方向的边沿离开能被准确记录和回放。

唯一允许的数据顺序应为：

```text
采集本 tick 的 pressed / released / held
  -> 读取 TickContext 与不可变关卡查询
  -> 更新方向队列、E 缓冲、autoDock 状态
  -> 继续/恢复 C2 路径推进
  -> 产生进入、离开、占用释放等边沿事件
  -> 开发 2 记录 tick 末 PlayerKinematics 与有序事件
  -> 生成只读 RenderSnapshot
  -> 共享时钟 advance()
```

禁止把键盘 `KeyEvent`、Canvas、系统时间或 `replay` 类型带入纯逻辑层。普通廊道不能因输入停车；`DOCKED` 是 autoDock 唯一的主动等待状态，也没有轮次提前结束键。
