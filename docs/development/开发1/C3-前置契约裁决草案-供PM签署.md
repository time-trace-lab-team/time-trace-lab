## A. `InputIntent` / `LogicalKey` 归属包

- **问题**：逻辑输入类型放哪个包，归属谁。
- **备选**：① `core/input/`；② `core/`（根）；③ 新建顶层 `input/`。
- **建议裁定**：**①`core/input/`**，开发一主责，纯 Java。
- **依据**：README 目标目录「`core/`：游戏循环、输入、碰撞、通用状态 [开发1]」——输入本就归 `core`；指南 §1.4「`core` 不得依赖 `Scene`/`Node`/`Canvas`/`KeyEvent`」——故必须是 JavaFX-free 的纯 Java 类型。独立子包避免 `core` 根被输入细节撑大。
- **影响**：开发二/三只读消费；若未来 PM 决定公共化，再提级，不影响字段。

## B. JavaFX `KeyEvent → InputIntent` 适配位置

- **问题**：把物理按键转成逻辑输入的那层放哪，谁写。
- **备选**：① `app/`（PM/集成）；② `ui/`（开发三）；③ 新增 JavaFX 边界包。
- **建议裁定**：**①`app/`**，由 PM/集成实现；开发一提供**映射表**与无头测试替身。
- **依据**：指南 §1.4「JavaFX 事件只在边界层转成不可变的逻辑输入；逻辑层不保存 `KeyEvent`」；README 目录「`app/`：启动、场景管理、状态切换 [项目经理/集成]」；卡 #2 把 `app` 列为开发一禁止路径。
- **映射表（开发一提供，供 app 使用）**：

  | 物理键 | `LogicalKey` | 说明 |
  | --- | --- | --- |
  | `W` / `↑` | `DIR_UP` | 同义合并 |
  | `S` / `↓` | `DIR_DOWN` | 同义合并 |
  | `A` / `←` | `DIR_LEFT` | 同义合并 |
  | `D` / `→` | `DIR_RIGHT` | 同义合并 |
  | `E` | `INTERACT` | 终端交互 |
  | `Space` | `PHASE` | 相位下潜 |
  | （其余 H/Esc 等） | 不进 `InputIntent` | 属 UI，开发三 |

- **影响**：开发一不在 `app/` 写代码；若 PM 最终决定由开发一实现该适配器，需**另开一张明确允许 `app/` 的任务卡**。

## C. 同 tick「进入 autoDock + 又按键」的唯一规则

- **问题**：进入驻留板的那一刻同刻又有方向新按下，算不算“离开边沿”。
- **备选**：① 进入先处理，同刻**新 `pressed`** 视为进入后的新边沿，**允许同刻离开**；② 同刻禁止离开（延到下一 tick）；③ 进入后忽略本刻全部输入。
- **建议裁定**：**①**。
- **依据**：README §三「进入瞬间必须清空旧方向队列，**只有之后新发生的有效方向键按下事件**才能让角色离开，避免玩家**按住前进键**时误触后立即滑出」——规则针对的是**旧键（held）**，并未禁止**新边沿**。用「edge vs held」单一判据即可覆盖，无需“同刻例外”分支，规则更单调、更易测。
- **补强（确定性）**：进入与离开同刻发生时，先发 `DOCK_ENTERED` 再发 `DOCK_LEFT`（排序键 `DOCK_ENTERED(0) < DOCK_LEFT(1)`），顺序确定。
- **影响**：`InputIntent` 必须严格区分 `pressedThisTick`（边沿）与 `held`（按住）；这也正是指南 §3.3 的要求。

## D. 双 autoDock 区域重叠的唯一规则

- **问题**：两个 autoDock 区域几何重叠，同一 tick 同时满足进入条件，进哪个。
- **备选**：① 运行时按稳定 `mechanismId` 升序取**第一个**；② 报错；③ 取几何上“先接触”的。
- **建议裁定**：**① 运行时规则 = `mechanismId` 升序取第一个**；**并由开发三在关卡加载时拒绝重叠配置**（数据校验优先，运行时规则兜底）。
- **依据**：指南 §3.3「不得依赖散列顺序/集合偶然顺序」——`mechanismId` 升序是稳定键；README §六 关卡数据合法性应由加载校验保证。
- **影响**：开发三需在 §1.2 autoDock 规格中明确“重叠 = 非法或按 ID 兜底”；开发一按此实现，不改机制代码。

## E. 失焦导致漏 `release` 的唯一规则

- **问题**：窗口失焦时收不到 key-up，`held` 会“卡键”。
- **备选**：① 失焦时把 `held` **全量记为 `releasedThisTick`** 并清空 `held`；② 保持 `held` 不变。
- **建议裁定**：**①**。
- **依据**：指南 §5.4（开发1）边界情况明确列「失焦导致 release 丢失」，必须显式处理；②会导致“按住不放”的幽灵输入，破坏确定性。
- **影响**：失焦后**无新 `pressed` 边沿不得触发任何动作**（含 autoDock 离开）；该规则应在 `InputIntent` 单测中固化。

## F. C1 装配责任（循环 + 输入 + 控制器接线）

- **问题**：谁把 `FixedStepLoop`、输入采集、`PatrolController` 接成一个可运行闭环。
- **备选**：① `app/` 内由 PM/集成装配；② 开发一在 `core/` 装配。
- **建议裁定**：**①**。
- **依据**：README 目录 `app/` = 场景管理 [PM/集成]；指南 §2.2 开发一禁止 `app/`；`core` 必须 JavaFX-free。开发一只提供纯逻辑端口（`TickUpdatePort`、`InputIntent`、`PatrolController`）。
- **影响**：联调由 PM 牵头；开发一为装配提供无头可测的端口与测试替身。

## G. 同刻多方向（单槽队列）

- **问题**：一 tick 内先后按下两个方向，队列留哪个。
- **备选**：① `directionEdges` **末位**胜出；② 首位胜出；③ 固定方向优先级。
- **建议裁定**：**①**。
- **依据**：README §三「新输入会替换尚未提交的旧方向」——后按的替换先按的 → 末位胜出。确定性的前提是 `directionEdges` 按**事件发生顺序**记录。
- **影响**：`InputIntent.directionEdges` 必须有序（`List` 而非 `Set`）。

## H. `DockEvent.reason` 取值集合

- **问题**：`DOCK_LEFT` / `OCCUPANCY_RELEASED` 的原因枚举取哪些。
- **建议裁定**：固定为 4 个：**`NEW_DIRECTION`（新方向键正常离开）、`ECHO_EXPIRED`（残影淘汰释放）、`SESSION_RESTART`（整局重开清空）、`LEVEL_EXIT`（退出关卡）**。
- **依据**：README §三/§七 列出的三种非主动离开（淘汰、重开、退出）+ 正常方向离开；`DOCK_ENTERED` 无需 reason。
- **影响**：**新增取值须 PM 批准**，开发一不得自造；`reason` 参与事件排序/诊断。

## C2 两个口子的裁定建议

### I. `PatrolController.advance()` 现硬编码返回 `CRUISING`

- **建议裁定**：**属 C3 范围**；`advance()` 增加“移动模式”输入（`CRUISING / DOCKED / SLOWED`），由 C3 依据 autoDock 占用与射线状态决定。
- **依据**：`MovementState` 三值已冻结（`CRUISING/SLOWED/DOCKED`）；C2 只交付恒速巡行，故当前硬编码 `CRUISING` 合理，扩展归 C3。
- **边界**：`DOCKED` 由开发一的 autoDock 逻辑置位；`SLOWED` 的**触发条件**来自开发三射线规则（命中 → `0.50×`、120 tick），C3 只做速度切换与记录，不重写射线规则。

### J. `PlayerKinematics` 是否新增“当前交互目标 ID”

- **建议裁定**：**不加**；交互目标经**事件**表达；`interactionTriggered`（现有布尔）保留用于动画。
- **依据**：`PlayerKinematics` 是 tick 末**规范帧**（README §九），只承载位置/朝向/移动/相位/动画；目标 ID 属机制语义，塞进帧会污染回放数据与渲染快照边界。
- **影响**：E 交互成功 → 发事件（终端交互），由开发二记录；帧里只留 `interactionTriggered`。
