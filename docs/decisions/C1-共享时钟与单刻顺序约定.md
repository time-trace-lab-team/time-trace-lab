## 1. 阶段枚举合并为单一 `core.GamePhase`

统一使用 `core.GamePhase` 作为**唯一正式阶段枚举**，补齐为 10 个值：

```text
BOOT / MENU / LEVEL_SELECT / TUTORIAL / READY / PLAYING / PAUSED / RESETTING / RESULT / FAILED
```

- 增加 `advancesLogic()`，**仅 `PLAYING` 返回 `true`**。
- 迁移 `RoundClock` 后**删除过渡版 `replay.RoundPhase`**。
- **不长期保留映射层**，避免两套阶段漂移。

### 1.1 由此产生的依赖方向（需记录）

本项使 `replay/` 首次依赖 `core/`。此前 `replay/` 为零依赖纯逻辑包。
确认后的单向依赖为：

```text
replay  →  core        （允许）
core    →  replay      （不引入）
```

后续所有新增共享类型应与此方向一致（见第 5.1 节）。

### 1.2 跨模块落地顺序（不可颠倒）

| 步 | 责任板块 | 内容 | 分支 |
| --- | --- | --- | --- |
| 1 | 开发 1 | `core/GamePhase` 补齐 10 值 + `advancesLogic()`（纯新增，不破坏现有 4 值用法） | `feature/core-c1` |
| 2 | 开发 2 | `RoundClock` 迁移到 `core.GamePhase`；删除 `replay.RoundPhase`；更新 `RoundClockTest` | `feature/replay-*` |

第 1 步为加法，先合入不会打破 `develop`；第 2 步必须在第 1 步合入之后进行。

## 2. `TickUpdatePort.stepOnce()` 必须返回结果

不采用 `void`，冻结为：

```java
TickStepResult stepOnce();
```

结果至少包含：

```text
NO_ADVANCE
ADVANCED
ROUND_END
```

`FixedStepLoop` 的补算规则：

- **仅在 `ADVANCED` 时**继续本渲染帧补算；
- 收到 `ROUND_END` 或 `NO_ADVANCE` **必须立即停止剩余步数**；
- **轮末未消费的补算额度直接丢弃，不能带入下一轮。**

## 3. 单 tick 正式顺序

```text
读取当前 TickContext（roundTick）
→ 消费该 tick 输入
→ 更新玩家、机关和残影
→ 发布并稳定排序该 tick 事件
→ 记录该 tick 结束后的规范状态
→ 生成只读渲染快照
→ 调用 RoundClock.advance()
```

推论（R2/R3 直接依据）：

- 先完整处理并记录 tick `0`，再 `advance()` 到 tick `1`；
- 处理并记录完 `D-1` 后，`advance()` 返回 `ROUND_END`；
- **有效记录恰好包含 `D` 条，`PlayerFrame.tick` 等于其列表索引，不存在 tick `D`**；
- 渲染快照在 `advance()` **之前**生成，即快照与当刻帧同源。

## 5. 待裁决事项（第 1、2 项属公共契约变更，需先闭合再编码）

### 5.1 🔴 `TickStepResult` 与既有 `replay.AdvanceResult` 重复

`replay/AdvanceResult.java` **已存在且已在用**（`RoundClock.advance()` 的返回类型，
21 条测试通过），其三个枚举值与本决策第 2 项**逐字相同**：

```java
public enum AdvanceResult { NO_ADVANCE, ADVANCED, ROUND_END }
```

若直接新建 `TickStepResult`，代码库将出现两个语义与取值完全相同的枚举，
属于技术指南明令禁止的「重复创建模型」。

**建议方案（择一，不要并存）**

| 方案 | 放置 | 依赖方向 | 代价 |
| --- | --- | --- | --- |
| **A（推荐）** | `core.TickStepResult`，删除 `replay.AdvanceResult`，`RoundClock.advance()` 改返回它 | 与第 1 项一致，全项目单向 `replay → core` | 开发 2 需改 `RoundClock` 签名与 12 条测试 |
| B | 保留 `replay.AdvanceResult`（可改名），`core.TickUpdatePort` import 它 | 引入 `core → replay`，与第 1 项方向相反 | 依赖双向，后期易循环 |

推荐 A：第 1 项已确立 `replay → core`，把结果类型也放 `core/` 可保持**唯一依赖方向**。

### 5.2 🟡 「补算额度丢弃」的测试归属需要拆分

第 2 项的规则跨越两个板块，测试不能只写在一边：

| 断言 | 归属 | 位置 |
| --- | --- | --- |
| 末刻反复 `advance()` 恒返回 `ROUND_END`、`roundTick` 恒为 `D-1`、`currentRound` 不自增、`phase` 仍为 `PLAYING` | 开发 2 | `replay/` 测试 |
| 一帧补跑 3 刻且跨轮末时，只消费到 `ROUND_END`，剩余步数丢弃且不带入下一轮 | 开发 1 | `core/` 测试（依赖 `FixedStepLoop`） |

### 5.3 🟡 R2 的三个状态枚举归属仍未定

第 1 项只统一了**阶段**枚举。`PlayerFrame` 仍需要
`Direction` / `MovementState` / `AnimationState`，三者均为玩家侧概念（开发 1 范围），
未在本决策中指定放置位置。**R2 主体仍被此项阻塞**，需单独裁决后开发 2 才能开工。
